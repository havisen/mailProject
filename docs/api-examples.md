# Send API examples

These examples use deliberately fake identifiers and content. Substitute secrets through a protected server-side environment; never put Bearer keys in shell history, URLs, browser JavaScript, or logs.

```sh
curl --fail-with-body --request POST 'https://mail-panel.example.test/api/v1/mail/send' \
  --header 'Authorization: Bearer ${MAIL_PANEL_API_KEY}' \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: auth-request-00000001' \
  --data '{"account_id":"acct_00000000000000000000000000000000","to":[{"email":"recipient@example.test","name":"Example Recipient"}],"subject":"Your sign-in code","text":"Use the code generated by the calling application."}'
```

Successful durable acceptance is HTTP 202 with `data.id`, `queued`, `send_before`, and `request_id`; it has no status URL. If the HTTP result is ambiguous, send the identical canonical request with the same key. Changing subject, recipients, bodies, or explicit deadline under that key returns 409.

The calling application owns code/link generation, expiry, storage, and verification. Prefer one recipient for authentication email. Choose an explicit `send_before` earlier than the code expires. Never include production codes or private mail in support fixtures.
